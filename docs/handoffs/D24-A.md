## 1. 定位结论

逐样本数据由 `evals/generation/evidence/2026-10-25/diagnose-b-batch.mjs` 从 B 公开的原始记录 ZIP 复算（ZIP 与每个记录都有 sha256），结果在 `d24-a-diagnosis.json`，不调用模型。

### 1.1 预算预约让生成或 REPAIR 提前结束（D21-A F3）
- 每次请求预约“输入 UTF-8 字节 + 512 + 4096”。实测输入 token 只有预约输入字节的 0.316–0.328 倍，输出通常 21–1,900 token。
- SHOW-01、SHOW-03、CAT-02、FAULT-CODE-03 都是被预约拒绝，不是额度真的用完：拒绝时已计费 30,040–38,255，剩余 11,745–19,960；旧规则需要 13,975–21,530（按前一次请求的大小估计，见 JSON 的 `proxy` 说明）。
- FAULT-CODE-01 是 12 次请求用完：第 2 轮修复没有请求可用。
- 根因之二：GENERATE 中模型每写一个文件就再读回一次（主批次每个样本 2–3 次，包括两个 READY 样本）。旧提示要求这样做，因为写入回执里没有内容；每次读回占一次请求，还把文件内容再放进之后每次请求的输入。

### 1.2 TASK-01/03 动作超时
- 两个样本都已构建成功、页面有可见内容、没有页面或控制台错误、没有被拦截或失败的请求，超时的是定位器等待：TASK-01 等 `getByRole('checkbox', {name:'买牛奶未完成'})`：生成的 label 是 `display:flex`，两个 span 之间会产生空格，实际可访问名称是“买牛奶 未完成”（离线 Chromium 复核，`accname-check.mjs`：flex 时只有带空格的名称匹配，block 时只有不带空格的匹配），TASK-03 等 `empty-state`，后面还有一个 `toggle-{{item.id}}` 模板占位符目标。
- 浏览器 worker 把定位器等待超时报为 `ACTION_TIMEOUT`，`RepairController` 把它归为 INFRASTRUCTURE，于是不进入修复。这与 D21-A F1（运行时错误让元素不渲染，同样报 `ACTION_TIMEOUT`）是同一个缺口。

### 1.3 CAT-01 验收动作无效
- 模型给了 25 个动作，上限 20，平台直接以 `AGENT_ACCEPTANCE_INVALID` 结束。B 的第一个批次里 TASK-01 也给了 21 个。

### 1.4 CAT-03 无效响应
- 两个 B 批次里 CAT-03 都在第一次 GENERATE 请求（输出 542 token 左右）得到 `MODEL_INVALID_RESPONSE`。平台从不保存回复内容，现有记录无法区分是截断、空内容、重复键、尾随数据还是根不是对象，**原因仍未知**，不猜测。

### 1.5 修复阶段协议错误（FAULT-CODE-02）
- 修复已成功写入后，模型回复 `{"type":"json_object"}`（10 个输出 token），而不是照抄带原验收动作的 `completionProposal`。D10-A 也见过同样的回复。

### 1.6 代码错误被误判为环境故障（F1）
- 见 1.2。主批次中 3 个代码故障都进入了修复，失败原因是 1.1 和 1.5；F1 影响的是需求样本和运行时异常类故障。

### 1.7 生成组件缺少标识
- 组件选择依赖页面/组件单一原生根上的静态 `data-ai-component`（D12-B 协议）。GENERATE 提示从未要求它，只有确定性 mock 和模板默认页带标识，所以真实版本的 catalog 对每个文件都是 `MISSING_COMPONENT_ID`（B 的 EDIT-04）。

### 4.4 仍然失败的三个

- **CAT-02、CAT-03：`AGENT_MODEL_BUDGET_EXCEEDED`，原因是输入上界，不是额度用完。** 本卡只把“输出”预约改成动态，输入上界（UTF-8 字节 + 512）没动。（由记录里的 `model.input` 与 `model.usage` 事件复算）

  | | 已计费 | 剩余 | 被拒请求的输入上界（至少） | 上一次请求的实际输入 token |
  | --- | --- | --- | --- | --- |
  | CAT-02（6 次后） | 30,088 | 19,912 | 21,624 | 6,757 |
  | CAT-03（5 次后） | 24,508 | 25,492 | 21,041 | 6,317 |

  被拒请求比上一次更大（多一份刚写入的文件内容），所以上界还要更高，放不进剩余额度；而实测输入 token 只有字节的 0.32 倍左右，实际下一次大约 8–9k。CAT-03 的 4 个计划文件已全部写完，只差 done，按真实用量能完成；CAT-02 还差 1 个文件和 done，按真实用量约 49–50k，临界。请求的固定部分约 10.7 KB（系统提示 5.3 KB、工具模式 2.8 KB、计划 2.6 KB）每次重复发送，加上累积的文件内容（占观察的 2/3），5 个以上文件的页面在已计费约 25k 后就放不下下一次请求。输入上界是现在唯一能保证总量不超过 50,000 的预约，放宽它会改变这个保证，不是本卡单方面能决定的。
- **FAULT-CODE-01：修复阶段又回复了 `{"type":"json_object"}`**（`AGENT_MODEL_PROTOCOL_INVALID`）。修复已两次 `files.update`，随后 `files.read` 了一次（提示说不要重读），第 9 次请求（REPAIR 第 5 次）回复 6 个 token，原文见私有捕获 `FAULT-CODE-01-wire/09-result.json`：`{"type":"json_object"}`，与 B 在 FAULT-CODE-02 看到的相同。该请求的 `response_format` 正是 `{"type":"json_object"}`，REPAIR 系统提示的第一句是 “Output exactly one json object.”，模型很可能把两者混成了回复。补丁因此没有冻结（“最终源码与注入源码不同”检查未通过）。同一批次里另外三次修复（SHOW-02、FAULT-CODE-02、FAULT-CODE-03）都正常完成，所以这是间歇现象。

## 5. 与 D21-B 联调组件标识

本卡给出的是**生成端**的修复，可信 catalog 的契约（D12）没有改：组件标识是单一原生根上的静态 `data-ai-component`，kebab-case，1–64 字符，catalog 由平台从真实源码解析，缺少标识不阻止 READY。
- 之前真实版本没有标识，因为 GENERATE 提示从未要求它。现在输入里有 `componentIds`，提示要求放在单一原生根上，REPAIR 要求保持不变。
- **真实证据**：9 个 READY 版本（7 个需求样本加 FAULT-CODE-02/03 的修复后版本）里的全部 15 个 `src/pages|components/*.vue` 文件，都有且只有一个静态 `data-ai-component`，值与宿主给的 `componentIds` 一致；没有缺失、重复、非法或绑定写法（`analyze-d24-batch.mjs` 对批次里保存的源码做的静态核对）。这**不是平台可信 catalog 的读数**：批次的临时数据库在样本结束时销毁，catalog 没有留存，原生根、不安全标记等判断没有在这里复核。
- **ID 来自计划里的文件名**（kebab-case，重名时按路径消歧，见第 2 节末），所以 B 的编辑用例期望的 `home-page`、`work-card`、`tasks-page` 只有计划用这些文件名时才一致。B 在对 `911943f` 的 review 里确认：B 当前的用例同时固定 componentId 和 sourceFile，不是按 catalog 选择；`PlanValidator` 只固定三条页面路由对应的页面文件，组件文件和 ID 前缀都可以变，所以合法的异名组件会被 B 的固定目标挡住。这是 B 侧需要改进的目标选择，不应要求 A 强制计划文件名，也不能记成 A 的模型失败。联调方式：由页面目标语义得到候选 ID，再经可信 catalog/服务端选择解析到文件，保持完整文件范围断言；定位不匹配、标识不可用、编辑任务本身失败分开报告。B 随后在 `755ed89`、`18da4d7` 里已改成这样做（见 B 的 `docs/evaluation-edit-handoff.md`）。
- B 还指出：GenerationEvalIT 的样本数据库用完即毁，只有批次 ID 不会产生可读取的六个真实编辑记录。后续要么保留可读的平台会话/真实编辑记录，要么明确标注来源的独立编辑评测执行方式；不能把源码重放当作原在线编辑。这一条不在本卡的修复范围。B 已把需求写成 `docs/evaluation-edit-handoff.md`（原版本的在线 API、所有者与审计会话、保留约定、同场采集），A 的提议（保留三个样本的转储，再还原成在线运行时，保持原身份）待 B 确认，确认前不动手。
